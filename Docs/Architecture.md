# Telescreen architecture

The full design is in the plan (`C:\Users\benvr\.claude\plans\i-want-a-new-mod-telescreen.md`). This file
describes what exists in the code and why it is shaped that way.

## Content (M0)

Everything is C++; the mod has no `Content` folder. Vanilla assets are referenced by path
(`Content/TSAssetPaths.h`).

- `ATSBuildableScreen` derives from `AFGBuildableSignBase`, the base of every vanilla sign, not from
  `AFGBuildableWidgetSign`. That keeps the vanilla sign hologram (`AFGStandaloneSignHologram`: wall snapping, auto
  poles, height adjust) working, because it only needs the sign base's dimensions and pole offsets, while leaving
  out the widget sign's text/icon layout, save data and interact UI.
- `ATSBuildableScreenSmall` / `ATSBuildableScreenLarge` copy the vanilla billboards' component layout, dimensions,
  pole offsets and clearance (values in `ReverseEngineering.md`). The screen face is an engine plane in the same
  place as the vanilla `ProxyMesh`, with a dynamic instance of the vanilla `MM_SignWidgetMaterial`, whose `SlateUI`
  texture shows the screen.
- Asset references are resolved at game instance start (`TSContent::ResolveVanillaAssets`, called from
  `UTSGameInstanceModule` at `INITIALIZATION`) and written into the class default objects, instead of being loaded
  in constructors: constructors run when the module loads, and loading Blueprint classes there is fragile. Because
  holograms and spawned buildables copy the class default's components, the meshes must be on the defaults before
  any world loads.
- `UTSDesc_Screen*`, `UTSRecipe_Screen*`, `UTSUnlockRecipe_Screens` and `UTSSchematic_Screens` are native
  subclasses of the game's descriptor, recipe, unlock and schematic classes. The schematic is an AWESOME Shop entry
  (25 coupons) registered by `UTSGameWorldModule`. Recipes mirror the vanilla billboard costs for now.

## Synced media (M1)

Two halves: replicated state that the server owns, and per-client playback that follows it.

### Server side: the queue

- `FTSMediaState` (on each screen, `Replicated` + `SaveGame`): queue, current index, `StartServerTime` (server world
  time when the item was at 0 s), pause flag and position, and a revision counter. Every client computes the
  position as `ServerTime - StartServerTime` from the game state's server clock, so they agree without any further
  messages.
- Buildables start network-dormant, so every change calls `FlushNetDormancy` before replicating.
- World time restarts each session, so `PreSaveGame` stores the position and `PostLoadGame` rebuilds the start time.
- A server timer moves to the next item when the current one's duration (plus one second) has passed. Items with an
  unknown duration (local files, failed lookups) and live streams never advance on their own.
- Players change the queue through `UTSRemoteCallObject` (enqueue, playback commands, screen name and picture fit).
  The server checks link length and scheme, the allowed sites, the longest-video limit and a per-player rate limit,
  and writes the requester's name itself. Refusals come back through `Client_Notice` and show in the panel.

### Client side: playback

- `UTSHostSubsystem` (game-instance subsystem, not on dedicated servers) starts `TelescreenHost.exe` from the
  runtime components on first use, in a kill-on-close job object, and talks to it over a named pipe
  (`Docs/HostProtocol.md`). It restarts the helper up to five times if it dies, and tells every session's listener.
- `FTSRuntimeComponents` finds and SHA-256-verifies the helper and yt-dlp per the shared spec
  (`D:/SFMod/Tools/RuntimeComponents.md`). The manifest (`Private/Runtime/TSRuntimeManifest.inl`) is generated by
  `Tools/stage_runtime.py`, so it always matches the staged files.
- `UTSScreenPlayer` (one per screen, client only) opens a helper session for the current item, sends the target
  position four times a second, uploads new frames into a transient texture and plays the audio ring through a
  procedural sound wave (`UTSStreamingSoundWave`, `PlayWhenSilent` so the helper's audio clock keeps running when the
  screen is inaudible).
- Picture fit (letterbox, fill, stretch) is applied when copying the frame into the texture, from the screen's real
  world size, so rescaled screens fit correctly without reopening the video.
- Audio is spatialised at the screen, full volume within half the screen's width and fading out over ten widths,
  times the player's hearing range setting. Volume follows the game's Master slider and mutes in the background.
- Only the `Screens playing at once` nearest screens within the play distance play; the others close their session
  and show their status until they're close again (the server clock keeps them in sync on return).
- Privacy: a video another player added loads automatically only if its site is in the player's allowed list (or
  their setting says otherwise); the panel offers "Load it anyway".
- When there's no picture, the screen shows a status card drawn into a canvas render target (screen name, title,
  Loading / Buffering / errors).

### UI

`UTSScreenPanel` is a native `UFGInteractWidget` that builds its UMG tree in C++ and opens through the game's
`AFGHUD::OpenInteractUI`, so input and focus behave like any vanilla building window. Links are looked up with
yt-dlp on the adding player's PC (title, duration) before being sent to the server; dedicated servers never run
yt-dlp.

## Browser (M2)

- **Helper:** `FBrowserSession` (`Helper/src/BrowserSession.cpp`) runs CEF 152 off-screen (Alloy style), loading
  `libcef.dll` from the `browser` runtime component (delay-loaded; CEF subprocesses are the same exe and get the
  component folder through a `--ts-browser-dir` switch). Frames (with `<select>` pop-ups composited in) go to the
  same video triple buffer as media; page audio comes from CEF's audio handler into the audio ring, so it plays from
  the screen and never through Windows. Input, navigation and browser state travel over the pipe
  (`HostProtocol.md`).
- **Hardening** (whoever is in control): clean profile unless "Keep browser logins" is on; only http(s), about, data
  and blob URLs; pop-ups stay in the view; downloads, file pickers, JavaScript dialogs, context menus and every
  permission request are refused. CEF's process sandbox is off for now (it needs CEF's bootstrap executable); it's a
  tracked M4 security item.
- **Pointer lock:** off-screen browsers reject the API, so an injected script stands in for it (`HostProtocol.md`).
  While a page holds the lock, the interactive window captures the mouse with high-precision (raw) movement and sends
  deltas.
- **Control:** a screen has a replicated mode (synced media or browser), controller and start URL. A player takes
  control through the remote call object; the server releases it when the controller leaves or stops. Until live
  streaming (M4), only the controller runs and sees the browser; everyone else sees "<name> is using the browser".
- **Browser size** follows the screen's real aspect ratio at the "Video quality" height, and resizes when the screen
  is rescaled.

### HUD picture and screen window

`UTSScreenWindow` shows one screen on the HUD in two states. **Pass-through** ("Show on HUD"): a small
hit-test-invisible picture in a corner. **Interactive** (panel "Use it in a window", the focus key F8, or the
screens list): a large centred window with UI-only input; mouse, wheel, keys and characters go to the browser, Esc
reaches the page, and holding Esc or pressing the focus key returns to the game. A shown screen ignores the play
distance and the screens-at-once limit, and its sound is 2D by default.

`UTSScreensList` (F9) lists every screen in the world, nearest first, with Show on HUD and Open window.
`UTSClientSubsystem` polls the two hotkeys.

### Settings

`UTSConfig` (SML mod configuration, converted to SML's editor classes at start-up like BoomBoxPlus): performance,
audio, privacy, "When hosting" (who may change videos, allowed sites, longest video, adds per minute) and
diagnostics (mirror the picture, in case a screen shows it flipped).
