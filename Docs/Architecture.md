# Telescreen architecture

The full design is in the plan (`C:\Users\benvr\.claude\plans\i-want-a-new-mod-telescreen.md`). This file
describes what exists in the code and why it is shaped that way.

## Content (M0)

Everything is C++; the mod has no `Content` folder. Vanilla assets are referenced by path
(`Content/TSAssetPaths.h`).

- `ATSBuildableScreen` derives from `AFGBuildableSignBase`, the base of every vanilla sign, not from
  `AFGBuildableWidgetSign`. That keeps the vanilla sign hologram (`AFGStandaloneSignHologram`: wall snapping, auto
  poles, height adjust) working, because it only needs the sign base's dimensions and pole offsets, while leaving
  out the widget sign's text/icon layout, save data and interact UI.
- `ATSBuildableScreenSmall` / `ATSBuildableScreenLarge` copy the vanilla billboards' component layout, dimensions,
  pole offsets and clearance (values in `ReverseEngineering.md`). The screen face is an engine plane in the same
  place as the vanilla `ProxyMesh`, with a dynamic instance of the vanilla `MM_SignWidgetMaterial`, whose `SlateUI`
  texture shows the screen.
- Asset references are resolved at game instance start (`TSContent::ResolveVanillaAssets`, called from
  `UTSGameInstanceModule` at `INITIALIZATION`) and written into the class default objects, instead of being loaded
  in constructors: constructors run when the module loads, and loading Blueprint classes there is fragile. Because
  holograms and spawned buildables copy the class default's components, the meshes must be on the defaults before
  any world loads.
- `UTSDesc_Screen*`, `UTSRecipe_Screen*`, `UTSUnlockRecipe_Screens` and `UTSSchematic_Screens` are native
  subclasses of the game's descriptor, recipe, unlock and schematic classes. The schematic is an AWESOME Shop entry
  (25 coupons) registered by `UTSGameWorldModule`. Recipes mirror the vanilla billboard costs for now.

## Synced media (M1)

Two halves: replicated state that the server owns, and per-client playback that follows it.

### Server side: the queue

- `FTSMediaState` (on each screen, `Replicated` + `SaveGame`): queue, current index, `StartServerTime` (server world
  time when the item was at 0 s), pause flag and position, and a revision counter. Every client computes the
  position as `ServerTime - StartServerTime` from the game state's server clock, so they agree without any further
  messages.
- Buildables start network-dormant, so every change calls `FlushNetDormancy` before replicating.
- World time restarts each session, so `PreSaveGame` stores the position and `PostLoadGame` rebuilds the start time.
- A server timer moves to the next item when the current one's duration (plus one second) has passed. Items with an
  unknown duration (local files, failed lookups) and live streams never advance on their own.
- Players change the queue through `UTSRemoteCallObject` (enqueue, playback commands, screen name and picture fit).
  The server checks link length and scheme, the allowed sites, the longest-video limit and a per-player rate limit,
  and writes the requester's name itself. Refusals come back through `Client_Notice` and show in the panel.

### Client side: playback

- `UTSHostSubsystem` (game-instance subsystem, not on dedicated servers) starts `TelescreenHost.exe` from the
  runtime components on first use, in a kill-on-close job object, and talks to it over a named pipe
  (`Docs/HostProtocol.md`). It restarts the helper up to five times if it dies, and tells every session's listener.
- `FTSRuntimeComponents` finds and SHA-256-verifies the helper and yt-dlp per the shared spec
  (`D:/SFMod/Tools/RuntimeComponents.md`). The manifest (`Private/Runtime/TSRuntimeManifest.inl`) is generated by
  `Tools/stage_runtime.py`, so it always matches the staged files.
- `UTSScreenPlayer` (one per screen, client only) opens a helper session for the current item, sends the target
  position four times a second, uploads new frames into a transient texture and plays the audio ring through a
  procedural sound wave (`UTSStreamingSoundWave`, `PlayWhenSilent` so the helper's audio clock keeps running when the
  screen is inaudible).
- Picture fit (letterbox, fill, stretch) is applied when copying the frame into the texture, from the screen's real
  world size, so rescaled screens fit correctly without reopening the video.
- Audio is spatialised at the screen, full volume within half the screen's width and fading out over ten widths,
  times the player's hearing range setting. Volume follows the game's Master slider and mutes in the background.
- Only the `Screens playing at once` nearest screens within the play distance play; the others close their session
  and show their status until they're close again (the server clock keeps them in sync on return).
- Privacy: a video another player added loads automatically only if its site is in the player's allowed list (or
  their setting says otherwise); the panel offers "Load it anyway".
- When there's no picture, the screen shows a status card drawn into a canvas render target (screen name, title,
  Loading / Buffering / errors).

### UI

`UTSScreenPanel` is a native `UFGInteractWidget` that builds its UMG tree in C++ and opens through the game's
`AFGHUD::OpenInteractUI`, so input and focus behave like any vanilla building window. Links are looked up with
yt-dlp on the adding player's PC (title, duration) before being sent to the server; dedicated servers never run
yt-dlp.

## Browser (M2)

- **Helper:** `FBrowserSession` (`Helper/src/BrowserSession.cpp`) runs CEF 152 off-screen (Alloy style), loading
  `libcef.dll` from the `browser` runtime component (delay-loaded; CEF subprocesses are the same exe and get the
  component folder through a `--ts-browser-dir` switch). Frames (with `<select>` pop-ups composited in) go to the
  same video triple buffer as media; page audio comes from CEF's audio handler into the audio ring, so it plays from
  the screen and never through Windows. Input, navigation and browser state travel over the pipe
  (`HostProtocol.md`).
- **Hardening** (whoever is in control): clean profile unless "Keep browser logins" is on; only http(s), about, data
  and blob URLs; pop-ups stay in the view; downloads, file pickers, JavaScript dialogs, context menus and every
  permission request are refused. CEF's process sandbox is off for now (it needs CEF's bootstrap executable); it's a
  tracked M4 security item.
- **Pointer lock:** off-screen browsers reject the API, so an injected script stands in for it (`HostProtocol.md`).
  While a page holds the lock, the interactive window captures the mouse with high-precision (raw) movement and sends
  deltas.
- **Control:** a screen has a replicated mode (synced media or browser), controller and start URL. A player takes
  control through the remote call object; the server releases it when the controller leaves or stops. Until live
  streaming (M4), only the controller runs and sees the browser; everyone else sees "<name> is using the browser".
- **Browser size** follows the screen's real aspect ratio at the "Video quality" height, and resizes when the screen
  is rescaled.

## Stream encoding (M3)

`FStreamEncoder` / `FStreamDecoder` (`Helper/src/StreamCodec.cpp`) are the encoder ladder M4 streams with: AV1, HEVC,
H.264 on NVENC / AMF / QuickSync, then SVT-AV1 in software (opt-in). Settings are for low latency: no B-frames,
constant bitrate, zero-latency/ultra-low-latency tuning, a two-frame rate buffer, keyframes on demand. SVT-AV1 needs
its low-delay prediction structure (`pred-struct=1`) to accept a bitrate cap.

Measured with `--selftest-encode` on Big Buck Bunny (RTX 3080 Ti, which has no AV1 encoder; 2026-10-22):

| Encoder -> decoder | Size, fps | Encode | Decode | Bitrate | Luma PSNR |
|---|---|---|---|---|---|
| hevc_nvenc -> hevc | 1440x720, 60 | 6.1 ms | 4.7 ms | 2.9 Mbps | 42.2 dB |
| hevc_nvenc -> hevc | 1920x1080, 60 | 8.4 ms | 9.7 ms | 5.7 Mbps | 43.4 dB |
| h264_nvenc -> h264 | 1920x1080, 60 | 8.0 ms | 5.2 ms | 6.0 Mbps | 42.6 dB |
| libsvtav1 -> libdav1d | 1440x720, 30 | 9.5 ms | 1.8 ms | 1.1 Mbps | 42.2 dB |
| libsvtav1 -> libdav1d | 1920x1080, 30 | 16.6 ms | 3.1 ms | 1.8 Mbps | 43.1 dB |

Conclusions for M4: default 720p at 30 fps (2-3 Mbps HEVC, or about 40% less with AV1); 60 fps as a game option;
viewers decode HEVC/H.264 with D3D11VA at 1080p60 (software decoding uses most of the frame budget there); software
AV1 is a sensible opt-in for controllers with CPU to spare.

The panel's **Stream test** (on a second screen while your browser runs on another) shows your browser through the
encoder and decoder on this PC, with live encoder, size, frame rate, bitrate and timing (`FLoopbackSession`).

### HUD picture and screen window

`UTSScreenWindow` shows one screen on the HUD in two states. **Pass-through** ("Show on HUD"): a small
hit-test-invisible picture in a corner. **Interactive** (panel "Use it in a window", the focus key F8, or the
screens list): a large centred window with UI-only input; mouse, wheel, keys and characters go to the browser, Esc
reaches the page, and holding Esc or pressing the focus key returns to the game. A shown screen ignores the play
distance and the screens-at-once limit, and its sound is 2D by default.

`UTSScreensList` (F9) lists every screen in the world, nearest first, with Show on HUD and Open window.
`UTSClientSubsystem` polls the two hotkeys.

### Settings

`UTSConfig` (SML mod configuration, converted to SML's editor classes at start-up like BoomBoxPlus): performance,
audio, "When you share" (browser, stream resolution, bitrate, frame rate and encoder, the curtain key), privacy, "Rules for this world" (who may
change videos, allowed sites, longest video, adds per minute, sharing browsers, stream rate cap) and diagnostics (mirror the picture, in case a screen shows it flipped).

## Live streaming (M4, game connection)

The controller's browser reaches other players through the game's own network connection; nothing else has to be
reachable or forwarded.

- **Who watches.** A viewer's `UTSScreenPlayer` opens a stream receiver session and tells the server
  (`Server_SetWatching`) when a browser screen is in range and active on its PC (the same play distance and
  screens-at-once ranking as videos; a HUD picture always counts). The server keeps the watchers per screen and
  replicates only their number (`mViewerCount`). The controller's player opens a stream sender for its browser
  session while the count is above zero and the curtain is off, so nothing is encoded or sent when nobody watches.
- **Sending.** Sender packets (HEVC/AV1/H.264 video, Opus audio) are cut into 768-byte `FTSStreamChunk`s so each fits
  in one game packet (the engine's limit is 1024 bytes with headers), queued, and sent with the unreliable
  `Server_StreamChunk` at most 750 KB/s and only while the connection isn't saturated. The engine silently drops
  unreliable RPCs on a saturated connection, so sending a keyframe's 50-150 chunks in one frame would lose most of
  them. If the queue holds more than 0.4 s of data the bitrate drops by 30% (every 3 s at most) and climbs back by
  10% after 10 s without congestion; past 1 s the queue is dropped and a keyframe is forced.
- **Relaying.** The server checks the sender is the controller, the curtain is off, sharing is allowed and the
  stream stays under "Most each stream may use" (token bucket, 0.5 s burst), then calls the unreliable
  `Client_StreamChunk` on each watcher (or delivers locally to a listen server's own player).
- **Receiving.** Chunks are reassembled per kind by packet id. A missing chunk or a skipped packet id resets the
  receiver to wait for a keyframe (no smeared pictures) and asks for one through the server; while waiting it asks
  again every 0.75 s. Measured with `Tools/stream_relay_test.py` (no network delay): 30 fps at 0.2% chunk loss,
  24-30 fps at 1%.
- **Rates.** The game's default rates (60-300 KB/s per connection) are shared with all gameplay traffic.
  `TSNetRate::Raise` lifts the net driver caps and connection speeds to 1.5 MB/s while a stream runs; the server
  re-raises on every relayed chunk because the listen-server net speed timer (`AGameNetworkManager::UpdateNetSpeeds`)
  can lower them again.
- **Privacy.** The first time a player opens or takes over a browser, the panel shows a notice that everything in it
  is visible to players nearby; pressing again accepts it (saved in the settings). The curtain (F10 or the panel's
  "Blank for everyone") stops the stream for everyone while the controller keeps using the browser; viewers see
  "They paused the stream". The panel and the window title show the controller how many players are watching.
- **Settings.** The sharer (When you share): stream resolution (lines, default 720), bitrate (default 2500 kbps),
  frame rate (30), encoder (best / prefer AV1 / HEVC / H.264 / software AV1), browser page size (lines the browser
  draws at, separate from the stream resolution). Viewers: watch other players' streams. The world host (Rules for
  this world): allow sharing, highest stream bitrate (default 8000 kbps, sound included), highest resolution (1080),
  highest frame rate (60). The server replicates its limits on each screen (`FTSStreamLimits`, refreshed when a
  player takes control and every 2 s while shared); the sharer's player encodes at the lower of its own setting and
  the limit (bitrate: limit minus 200 kbps for sound and chunk overhead). Changing the resolution, frame rate or
  encoder restarts the sender; a bitrate change applies at once. The helper scales taller frames down with swscale's
  area filter, keeping their shape (`FSenderParams::MaxHeight`); the send pace and the raised net rates follow the
  bitrate (`TSNetRate::RateFor`: at least 1.5 MB/s, otherwise twice the stream).

The helper's sender seeds itself with the browser's current frame when it opens (`FrameTaps::SetRefresh`), so a
viewer joining an unchanging page sees it at once; unchanged pages are re-encoded once per frame interval and get a
keyframe at least every 4 s.

Not done yet: WebRTC / direct connections to offload the server, CEF's process sandbox.

## Local videos and streaming synced media

**Local videos** (`Private/Screen/TSLocalVideos.cpp`). A queue entry without `://` is a file. Each PC plays it from
the full path when that exists there; otherwise from a file with the same name (case-insensitive) anywhere in that
player's videos folder (setting "Videos folder", or the Videos tab's Change folder button), so copies in different
places (a Plex folder on F: or C:) still match. The folder is indexed on a worker thread (file name -> path, at most
200,000 files) the first time it's needed; a miss re-indexes at most every 30 s. Folder and file pickers are the
Windows `IFileOpenDialog` on their own thread, so the game (and a listen server) keeps running.

**Streaming synced media.** A player whose PC can't play the current item (the file isn't there, or its session
fails) watches it as a live stream from a player who plays it, through the same path as shared browsers:

- Every PC reports once per item whether it plays it (`Server_ReportMedia`: plays / can't, and whether it agrees to
  stream, setting "Stream videos to players who can't play them"; the world host's "Allow sharing" applies). A
  different current URL resets the reports, the streamer and the watchers (`CommitMediaState`).
- The server picks the media streamer from the players who play it and agree: the current one while it can,
  otherwise the player who added it, otherwise any (`ChooseMediaStreamer`), and replicates it (`mMediaStreamer`).
- Players who can't play it open a stream receiver and watch (`Server_SetWatcher` accepts watchers in synced mode
  while there is a streamer); the stream sender is `GetStreamSender()` (the controller in browser/window/desktop
  modes, the media streamer for synced media), which the chunk relay and keyframe requests use.
- The streamer's player opens a stream sender on its media session while anyone watches, and keeps the screen
  active (playing) wherever the streamer is. The helper's media session publishes its shown frames and its audio to
  the taps; audio is handed to the taps as the game reads it from the ring, so it stays in step with the picture
  (the decoder writes up to 0.3 s ahead).
- Pause and seek follow the streamer's synced playback; viewers see it about half a second later. Privacy-blocked
  items (Privacy setting) aren't streamed.

The stream is re-encoded (the encoder ladder), not the file's own video: files are encoded for storage (5-15 Mbps for
1080p, a keyframe every few seconds, 10-bit, AC3), while the stream fits the bitrate cap and recovers from losses with
a keyframe on demand.

Verified outside the game (2026-10-22): `--selftest-stream-file` on a 10-bit HEVC 1080p MKV with AC3 5.1: hevc_nvenc
1280x720 at 30 fps, 2.9 Mbps, no losses, audio consumed throughout.

## Subtitles

Per player: where they show (`SubtitleMode`: off, on the screen, on the HUD, both) and the preferred language
(`SubtitleLanguage`). The helper finds a video's tracks when it opens it (`Helper/src/Subtitles.cpp`):

- **Web videos:** yt-dlp prints `%(language)s`, `%(subtitles)j` and `%(automatic_captions)j`; site subtitles are all
  offered, automatic captions only for the video's own language and the preferred one (YouTube lists every
  translation). The best format is used: json3 (YouTube), then WebVTT, then SRT. YouTube's automatic captions come as
  short overlapping events; the player shows the last two that are on.
- **Files:** text subtitle streams inside the file (SRT, ASS/SSA, WebVTT, mov_text: FFmpeg's subtitle decoders give
  ASS dialogue lines, styling removed), and `.srt` / `.vtt` files next to the video named like it (`Movie.srt`,
  `Movie.en.srt`). Picking an embedded track reads that track from the whole file on a worker thread (the playing
  demuxer is already past what has played); the demuxer's own packets cover the time until then.
- Tracks go to the mod (`SubtitleTracks`); the player picks one in the preferred language (people-made first, then
  automatic; three-letter codes from files are matched too) when subtitles are on, or the panel's track buttons pick
  one (`SelectSubtitles`). Cues arrive sorted (`SubtitleCues`, replace or add; added cues are de-duplicated).
- **On the screen:** while a line is showing, the screen's texture is a canvas render target that draws the video
  texture and the line(s) over it (engine large font, outlined, about a sixteenth of the picture's height per line),
  redrawn with every composed frame and whenever the line changes; otherwise the video texture itself.
- **On the HUD:** `UTSSubtitleOverlay`, bottom centre, for the screen shown on the HUD or else the nearest screen
  within the play distance that has a line (`UTSClientSubsystem`, 10 times a second).

Not yet: picture subtitles (PGS, VobSub), subtitles for viewers of a streamed video.

## Direct connections

Opt-in for both ends (`DirectStreams`), allowed by the world host (`AllowDirect`). Live streams still start through
the game connection; a direct link takes over when it comes up, and the game connection takes over again when it
goes down.

- **Helper (`Helper/src/Direct.cpp`, `Upnp.cpp`):** one UDP socket per helper (port `DirectPort`, 0 any), opened on
  first use: a STUN binding request (stun.l.google.com, then stun.cloudflare.com) gives the public address, UPnP
  (SSDP discovery, WANIPConnection/WANPPPConnection AddPortMapping, 2 h lease, removed at exit) opens the port when
  `DirectUpnp` is on. Candidates: the UPnP external address, the STUN address (and the forwarded port number on it),
  the LAN addresses, 127.0.0.1.
- **Setup through the server:** the viewer's player sends its candidates (`Server_DirectRequest`); the server checks
  it watches, makes a link id and a 128-bit key, and asks the stream sender (`Client_DirectRequest`, or the local
  delegate on a listen server); the sender links its sender session to it and answers with its candidates
  (`Server_DirectAnswer` -> `Client_DirectAnswer`); the viewer links its receiver session.
- **Connecting:** both helpers send authenticated probes to every candidate every 0.2 s; the first authenticated
  packet from the other side sets the address in use (another working path takes over only when it goes quiet for
  2 s) and the link is up. Keepalives every second; down after 6 s of silence or 12 s without connecting.
- **Data:** each encoded packet is cut into 1,100-byte chunks (kind, flags, pts, codec, packet id, index, count),
  AES-128-GCM sealed (header as associated data), and paced at up to 4 MB/s per link; the receiving helper reassembles
  them and feeds the receiver session directly. A lost video chunk drops packets until the next keyframe and tells
  the mod, which asks for one through the server (as on the game path).
- **Server relay:** a viewer whose link is up tells the server (`Server_SetDirect`); the server stops relaying to it
  and replicates the number still relayed (`mRelayedViewerCount`); at 0 the sender doesn't queue chunks for the
  server at all. The game path's bitrate adaptation doesn't see direct links (no feedback yet).

Verified outside the game (2026-10-22, `--selftest-direct`): two hubs in one process, STUN answered, link up in
0.01 s over the LAN address, 180 of 180 packets (2.1 MB, 3 keyframes) at 3 Mbps.

## Window mode (M5)

`FWindowSession` (`Helper/src/WindowSession.cpp`) shares one top-level window the controller picks from the
panel's list (`ListShareableWindows`: visible, titled, not cloaked, not tool windows, not the game itself).

- **Picture:** Windows Graphics Capture (C++/WinRT, free-threaded frame pool on a D3D11 device). Frames are copied
  through a staging texture, scaled with swscale's area filter to fit 1920x1080, published at most 60 times a
  second to the session's video buffer (the controller's own screen) and the frame taps (the stream sender). The
  capture reads the window's own surface, so the window can sit behind the game; a minimised window stops
  producing frames, and the session says so.
- **Sound:** process loopback (`ActivateAudioInterfaceAsync` with `AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK`,
  the window's process tree, 48 kHz float stereo). Windows mutes/volume apply before the capture, so the window
  can't be silenced locally; the controller hears it from the window and only viewers get it from the screen.
  Needs Windows 10 build 20348+ / Windows 11; otherwise there is no sound and the log says why.
- **Input:** posted window messages (mouse to the deepest child under the point, keys and characters to the
  window thread's focused control). Apps that read raw input (games, VM consoles) ignore it.
- Positions from the mod map through the picture's letterbox/crop back to frame pixels (`ToSourcePixels`).
- Measured with `stream_relay_test.py window:Spotify`: 1920x1044 HEVC at 1.9 Mbps, 20-31 fps at 0.5% chunk loss.

## Roles and world host tools

See Security.md for the full split between the world host (rules for everyone) and the sharer (their own PC).

Host settings decide the lowest role that may use the browser (default everyone) and share a window (default
trusted players and the host): everyone, trusted players (a comma-separated name list) or the host. The host is the
listen server's own player; on dedicated servers, players the server marks as admins (`AFGPlayerState::IsServerAdmin`).
Other limits: taking over a screen in use (on/off), screens in use at once in the world (default 4), and each
player controls one screen (taking another releases the first). The host and admins can stop any screen's browser or
window from the panel. All checks run on the server (`UTSRemoteCallObject::MayUseMode`); RPC validation only rejects
messages the mod never sends, because a failed validation disconnects the player.

| `Widget_ListButton` | queue, shareable windows, saved remote desktops | `mTitle`, `mDescription`, `DescVisibility`, `iconVisibility` (collapsed), `mIsSelected` (the playing video), `mRecipeButton` |
| `Widget_Window_ContentBackground_DarkMode` | panel and dialog background | (layered under the content) |
| `Widget_StandardButton` | buttons | `mText`, `SetText`, `SetButtonStyle(orange, light, no background)`, `SetIsDisabled`, `mButton` |
| `Widget_StandardButton` (orange = selected) | mode tabs, picture fit, Screen settings | as buttons. `Widget_SlidingTabs_Button` takes its label and width from a `Widget_TabsContainer`, so standalone it shows as an empty box; it is only probed for the bold font |

The panel is sized to the viewport (about 62% wide, 1000-1400 UI units; pages up to 80% of the height) in two


## Screen sound in Wwise

Like BoomBoxPlus (its `Docs/WwiseMusic.md` has the bank format details), each screen's sound plays through the game's
own Wwise on the screen's own `UAkComponent` (created by class name `/Script/AkAudio.AkComponent`, so the mod imports
nothing from AkAudio), at the screen's centre, with its attenuation scaled by the screen's width (8 m = 1, times the
Hearing range setting) through `SetAttenuationScalingFactor`. Rooms, reverb, occlusion and the game's volume sliders
(the Boom Box mix, which the bank comes from) apply.

- `TSWwiseScreens::EnsureReady` builds the bank from the first `Play_Boombox_*.bnk` with one event whose Play action
  targets a sound: that sound's source becomes Audio Input (plugin `0x00C80002`, with its plugin settings object and
  the 4-byte parameter size), every object gets a `TS_Screen_<old id>` id, the bank `TS_Screen_Bank`, the source
  `TS_Screen_Input`. Then it registers the built-in Audio Input plugin (another mod may already have) and loads it.
- **Shared callbacks.** Audio Input has one set of callbacks for the whole game, so Telescreen and BoomBoxPlus share a
  dispatcher: each registers an `ISFModWwiseAudioInputSource` (`Private/Audio/SFModWwiseAudioInput.h`, identical in
  both mods) with `IModularFeatures`, and whichever mod installed the callbacks asks every source in turn; a source
  answers only for its own playing ids. Unknown ids get silence and 48 kHz stereo.
- Samples come straight from the helper's audio ring (`FTSAudioReader`), scaled by the screen volume (0 while muted
  in the background); the game's sliders apply on the bus.
- A HUD picture with "Hear it everywhere" moves its emitter to the camera every frame.
- If Wwise ends the sound itself it is posted again; two quick ends in a row switch that sound to the Unreal path
  (`UAudioComponent` + `UTSStreamingSoundWave`), which is also used when the setting is off or Wwise isn't reachable.

## Viewer control and markers (M6)

Grants, the server relay and the input filter: Security.md. Input path: a granted viewer's screen window sends its
events through `UTSScreenPlayer`'s usual input functions, which turn them into `FTSViewerInput` (positions 0-65535
across the picture) for `Server_ViewerPointer` (moves, unreliable) or `Server_ViewerInput` (the rest, reliable); the
server checks the grant and rate, then `Client_ViewerInput` on the sharer, whose player filters and applies them as if
they were its own, mapping positions through the picture's fit. Markers: the server sends viewer cursors (at most 15 a
second) and pings to everyone watching and the sharer (`Client_ScreenMarker`); each PC draws them into its screen
texture (an arrow for a cursor, a growing ring for a ping, in a colour from the player's name) and the screen window
labels them with the name.
